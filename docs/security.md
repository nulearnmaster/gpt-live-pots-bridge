# Security and operations

This bridge is a **single-owner prototype**, not a public dial-in or multi-tenant voice application. Web uses a separate private HTTPS listener; SIP uses a signed webhook. Signing a webhook authenticates OpenAI's delivery, not the person on the phone. Caller ID, asserted URI, display name and SIP headers are never authorization. TLS/SRTP protect the trunk hop, not every upstream carrier hop, and the provider processes the media and can see or retain keypad events. The first signed pending call after arming can reserve the attempt; attackers reaching the route can race or consume it. Use a private/restricted trunk with provider-side account/network restrictions, restrictive ingress and an approved spend cap. Don't depend on obscurity of a phone number or project ID. Do not use the prototype when a spare public number would allow untrusted callers to run up unacceptable costs.

### Boundaries

- Internet-facing: one reverse-proxied `POST /webhooks/openai`; raw-body signature and 5-minute header timestamp verification, an additional short event-age window, no unsigned decisions, and bounded headers/body, request time, connections and call durations. Rate-limit and size-limit at your proxy as well. Never log bodies, headers, or proxy authorization. Synchronize clocks. Reject unsanctioned OpenAI project events by using a dedicated webhook secret and project-scoped API key. Use a separate webhook subscription for any legacy deployment.
- Inbound call accepted only while armed; one attempt and one PIN use; unpaired timeout ~45 seconds, paired service limit 20 minutes. An unpaired call can still accrue provider costs. Independent input mute and DTMF controls run over Live sideband; audio prior to mute might reach the provider. PINs are only entered via keypad; never spoken or sent to the agent. The plaintext code is displayed only on the operator TTY, and the verifier is in memory. Do not share your terminal or record scrollback. The bridge uses neither SIP metadata nor speech as a fallback.
- Use an isolated Unix account for `serve` that cannot read or run the Pots user's environment/Pots directories. An ordinary pilot on the same UID does **not** isolate the agent from a compromised bridge process. Use a dedicated worker group containing only the service account and the authorized Pots user: put **only** the worker socket in a directory owned by the service account with that group and mode `2750` (setgid, owner writable, group traverse/read, no group write). Set `VOICE_SHARED_GROUP=yes` to grant `0660` on that socket. Keep state and admin socket in a separate service-owned `0700` directory; use trusted, non-writable-by-others ancestors. Don't forward sockets via reverse proxies, tunnels, or containers with shared mount access. Don't give the API key/webhook signing secret to the Pots user/worker process. Processes sharing the trusted worker user's permissions can claim or complete tasks; the socket is not a sandbox for untrusted local plugins or users.
- Worker uses a fixed executable and pinned, verified destination from local configuration; it passes a static wake note and sends validated text on stdin without invoking a shell. Only accepted presets can cross the handoff. Results never return as arbitrary speech; only fixed status/receipt is sent back to the open session. Links must match an operator-configured origin, have no search/hash/credentials, and are never fetched by the bridge. Host artifacts on an authorized origin you control; do not allow open redirects or use signed/token-bearing links. Ordinary result text should be a generic draft, not secrets or private personal data.

### Private web boundary

- Enable web explicitly and proxy only a dedicated owner-only HTTPS origin to its separate loopback port, as in the [mobile runbook](web-smoke.md). Use a restricted VPN/ACL (never public Funnel); preserve the public-facing `Host`, and supply `X-Forwarded-Proto: https` only from a trusted TLS terminator. Those headers are not user authentication. Do not serve this from a shared application origin or give other users/processes access to the loopback listener, admin socket, or TLS terminator. Local processes capable of spoofing proxy headers are outside the proxy trust boundary; the one-use web token is still required.
- The private admin socket issues one random one-use link (2 min), not a reusable API credential. The fragment is never sent in navigation, the page strips it from browser history, and redemption exchanges it for a same-origin `Secure; HttpOnly; SameSite=Strict` cookie with a 2-minute start deadline. Copying a URL or using synced history can still disclose a fresh grant: keep it private. The service only keeps scoped cookie/grant verifiers in memory. An explicit browser tap and an affirmative consent value are required to create a session; do not share private access with anyone else. Exact `Host`, HTTPS proxy header, browser `Origin`, optionally Fetch Metadata, known routes, JSON plus size/time limits, connection cap and in-process rate limits are checked. A persisted minimum 30-second interval separates paid web attempts, and one call slot covers web and SIP.
- The only media input is an audio track on native WebRTC (no camera or turn uploads). The broker returns only SDP; the browser independently receives native lifecycle events that can contain provider session ID and configuration metadata, never an API credential. It may not send commands on the data channel. Inputs to the broker cannot set the provider model, voice, tools, URL, destination or ID. Voice is selected from a small operator-side allowlist; no provider credentials enter the browser. The WebRTC answer and reflected media can contain sensitive ICE/material/media; they are neither logged nor stored by the bridge. Use browser/OS permission indicators to check capture; the provider processes the media.
- End disables further task acceptance and local mic capture immediately. The bridge requires provider `session.closed` to confirm web end; a 20-second page lease and an approximately two-minute pilot timer bound local behavior. The browser has no lock-screen/background guarantee. Persistence distinguishes create-in-flight (possibly billable with unknown ID) from a known active ID. The bridge never replays a potentially billable create; a reservation with ambiguous create/close blocks both transports until confirmed. Retain it and reconcile via the [runbook](web-smoke.md); do not drop the queue or infer clean close from a lost connection.

### Operations

- One service instance per state DB. Protect database and WAL files, process environments, host backups, and logs with filesystem permissions and disk encryption where appropriate. SQL pruning removes closed web reservations and SIP call dedup keys after 7 days (unconfirmed web reservations persist) and successfully delivered result records after 30 days; undelivered/claimed jobs are retained for reconciliation. This is not secure erasure of SQLite pages and backups, and doesn't erase copies held by OpenAI, SIP provider, Pots, or Telegram. Review and obtain consent where required before use.
- Treat `queued` as a committed receipt, `claimed` as responsibility picked up, `done` as stored result, `delivery_recorded` as downstream acknowledgement. No text/audio played on the call is proof of recipient hearing. When a wake/send acknowledgment is lost, the worker retries the same stable ID. Telegram's external send may still be ambiguous after a crash; review any uncertain delivery, don't rotate IDs or recipients to force a retry.
- After a service crash, a stale socket file may remain. Stop and verify the old process and listeners are gone, then remove only those two configured stale socket files. Do not remove the SQLite DB/WAL to make restart work. Startup attempts SIP REST hangup for recent SIP calls and sideband close for known unclosed web calls; contact the provider if this fails. Always use provider-side spending alarms and duration caps because process/network loss can outlast the bridge's local timer. Calls aren't reattached after disconnect; processing resumes only for accepted jobs.
- No job cancellation is inferred from speech interruptions or hangup. Stop using an unexpected or unsupported request; adjust presets via code review; don't add a generic exec, arbitrary workflow input, or interactive voice approval. This bridge ships no remote authentication for a worker; anyone building a remote worker adapter must add mutually authenticated transport, fixed identities/rights, and its own review.
