# Talk to your existing Pots agent (private owner mode)

With this separate opt-in, the same saved mobile URL can take natural questions and harmless draft requests for **your existing Pots main agent**. Examples: “지난번 텔레그램에서 내가 부탁했던 게 뭐였지?” or “그 주제에 맞는 체크리스트 초안 써줘.” There is no required phrase or separate login. GPT-Live supplies real-time audio, interruptions and client delegation; the current Pots main agent supplies the substantive answer. The main agent uses its own permitted context and, if needed, reads the owner's allowed prior chats (e.g. Telegram and terminal) using its existing access. The bridge does not import or synchronize chat history into OpenAI Live, add a new agent, or make a separate model request for the answer.

When a recent submitted request is durably queued, the bridge sends a short correlated receipt while you can continue talking. If the main agent supplies a short answer explicitly marked safe to speak, the service sends it as a `session.commentary.append` on the **same** live delegation. Otherwise it sends status only. Ending the call does not cancel accepted work; the worker still sends its result to the configured private Telegram DM. A different call cannot receive that old spoken reply. The main agent may complete directly or hand off a harmless text draft to a one-off child.

## Enable after operator review

1. Set up the [private trusted-owner bookmark](owner-bookmark.md), including the authenticated exact owner/phone gate. Context mode is **not** available on SIP, invitation web, or a public origin. Browser JSON cannot change the mode, the model, bot or recipient. Keep the same private URL, one explicit paid Start, normal Live voice rate, and no application elapsed-time limit.
2. Add the [owner-context dispatch agreement](../examples/pots-dispatch.md#optional-owner-context-existing-main-agent) to the selected **existing** main agent. Give it only the allowed local history lookup and claim/complete operations required for this flow. Verify that the Telegram destination belongs to the same owner. Use the canonical exact bot name (e.g. `omarchy`, if that is your existing bot) and private Telegram place. A contextual wake is a separate scheduling event; the existing main agent must select the relevant history. It is not guaranteed that a wake's prompt contains the latest history without that lookup.
3. On **both** bridge service and worker, set `VOICE_POTS_BOT` and `VOICE_RESULT_ADDRESS` to those same fixed values. Use the existing permissioned worker socket, distinct service and agent/worker principals, and fixed executable paths. The bridge gets those two strings only to bind queued context jobs to that exact route; it does not get the Pots executable or a Telegram credential. The worker does not get an OpenAI/proxy key. Do not accept either setting from any voice request. A worker with a different configured bot/DM, or without the context flag, leaves those contextual wake/delivery records untouched. The socket itself trusts its authorized Unix principals; the route binding does not isolate other local processes that can already call that socket. Neither key rotation nor a restarted service changes a receipt's bound route; reconcile outstanding tasks before changing the bot or inbox.

   ```sh
   # Separate explicit approval is required for actual Live and Pots costs.
   node src/cli.mjs serve --enable-paid-webrtc --enable-trusted-web-owner --enable-owner-context
   node src/cli.mjs worker --enable-pots-effects --enable-owner-context
   ```

   Use one service instance per DB. Take a protected backup with the previous service stopped before first enabling this version. It migrates existing `jobs` rows to allow distinct ordered contextual turns while retaining legacy receipts and once-per-preset uniqueness. Avoid switching to older code with outstanding contextual requests: its legacy list/dispatch procedures don't know their privacy and routing rules.

## Scope, privacy and limits

- Initial scope: read only the relevant owner-visible chat context and answer without secrets, or produce an innocuous draft in text. **Voice cannot approve or authorize execution, external sends, account/file changes, spending, purchases, deploys, disclosures, permission changes, or third-party tools.** The built-in bridge exposes only an immutable queue type, receipt, and fixed destination; no shell or gateway executor. Its receipt does not imply the agent has started or approved any action. The trusted existing main agent remains responsible for interpreting/rejecting the plain-text request and not using elevated permissions. Its instructions and token checks are not a sandbox for a privileged or adversarial agent. Don't enable this if that risk is unacceptable.
- Only the short matched request is stored durably for the agent's protected claim. Unaccepted conversation, raw audio, and assistant transcripts are not stored by the bridge. Routine `/list`, wake arguments and inbox messages do not echo the contextual request. Normal completion erases the logical request field, not earlier copies in SQLite pages/WAL, logs, Pots history, backups or provider retention. The normal results retention policy applies. The optional `speech` sentence goes only to the active Live session and isn't stored by the bridge or added to the private result; `summary` and approved link are for the private inbox, never the provider. Avoid PII/credentials in all inputs. Pattern checks only reject some recognizable secrets, not every confidential sentence. Adding spoken output to a call necessarily gives it to the provider and anyone who can hear the device. Keep content strictly safe to speak.
- Live emits timestamped input fragments and a client delegation ID/offset, **not** a definitive addressed-turn/completion marker or command text. The bridge groups only a recent, contiguous non-overlapping fragment window (up to 12 seconds; maximum stored text 500 characters), deduplicates accepted turns, and caps outstanding contextual jobs at eight per bound route. Ask one short question at a time, in ordinary speech. Background/quoted speech, pauses, late fragments, and ASR errors can still change which text is picked; if unclear, repeat or correct. Live is instructed not to answer substantive questions independently. The speech model can still talk or miss a delegation; its commentary API requests speakable context, not deterministic playback or proof the caller heard it. A private inbox result is the reliable fallback after an accepted receipt.
- The offline suite uses mock provider events, SQLite, a fake Pots executable for the exact `--bot` and DM route, and simulated main-agent/child completion through the real local CLI. It cannot show that the installed agent obeys the agreement or that the provider delegates a live user's words and speaks the reply. For an approved **parked** real test, first put a harmless non-secret reminder in the owner's Pots chat, ask about it by voice without a marker, compare the short readback with the same chat agent's answer, and end a follow-up draft before it finishes. Confirm the same bot delivers both to the expected private inbox, no old answer is spoken in a new call, and no external actions are taken. Use the [ordinary mobile smoke](web-smoke.md) for audio, cost and background limitations.
