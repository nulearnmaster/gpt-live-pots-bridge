# Private mobile web pilot (manual; potentially billable)

This is an **unrun** acceptance checklist for a real handset. `npm test` and `npm run demo` do not require or spend provider/Pots credits. Before real activation, confirm project access to `gpt-live-1.1`, current API prices, and a separate Pots budget. The API page lists **US$0.05/min active** as of 2026-11-25, so up to two minutes of Live voice is estimated at **~US$0.10**. The default startup requests 15 seconds of duration charge, credited if the session runs, not an extra 15 seconds of an active session. The server requests close at ~115 seconds from the attempt and allows up to five seconds to confirm. An estimate and bridge timer are **not a provider-side hard dollar cap**; setup failures, outages and missing close events can affect duration/cost, and taxes and Pots model usage are separate. Monitor provider usage, use a dedicated project, and do not enable if its available limits and budget controls are insufficient.

## Put just the web bridge behind private HTTPS

1. Use the [shared Pots/state setup](../README.md#opt-in-real-sip-and-shared-pots-setup). The bridge and worker should run as separate principals as described in the [security guide](security.md). Inject the key into `serve` privately; don't put it in shell history, proxy configuration, browser, or worker. Web-only mode does not read a webhook signing secret. Set `VOICE_WEB_ORIGIN` to one exact HTTPS origin without a trailing slash or path; `VOICE_WEB_PORT` defaults to `8789`. Use a dedicated origin, not a path on a host with other apps. Optional `VOICE_WEB_VOICE=marin` (default) or `coral` is fixed for a new session, not set by the browser. Marin is the documented Live default, chosen here as a feminine-sounding voice; perception varies with listener/language, so confirm on the phone. No gender identity is claimed for a voice.
2. **Recommended:** private Tailscale Serve on a dedicated tailnet node/address, with MagicDNS and HTTPS certificates enabled as required by Tailscale. Approve all network/service changes and any costs separately. Install/connect the phone to the same tailnet, configure the tailnet's access policy to allow **only the owner or managed owner devices** as source for the dedicated bridge node/tag and pilot HTTPS port, and verify a second unapproved tailnet identity cannot connect. Tailscale rules are additive: a broad `*` grant still makes the listener reachable; remove or narrow it for this destination before use. Example policy fragment (substitute real values and review your full policy):

   ```json
   {"grants":[{"src":["owner@example.com"],"dst":["tag:voice-bridge"],"ip":["tcp:8443"]}]}
   ```

   In an authorized setup, on an **unused dedicated port** with no Funnel on this node/port, the proposed mapping is:

   ```sh
   # Proposed only; inspect tailscale serve/funnel status and --help first.
   tailscale serve --https=8443 http://127.0.0.1:8789
   # Example VOICE_WEB_ORIGIN: https://bridge.your-tailnet.ts.net:8443
   ```

   Verify the command is **Serve (tailnet only)**, not **Funnel (public)**. Verify the phone's browser sees a valid certificate and the page is inaccessible outside the authorized tailnet scope. Use the exact hostname and port logged by Serve. Do not replace the origin with the machine's IP or ignore certificate warnings. Tailscale HTTPS DNS names can be visible in public certificate transparency logs: use a non-sensitive hostname. At test end stop just the pilot mapping (Ctrl-C for foreground Serve) without touching other services. No tunnel, DNS, policy, or service is created by this repo.
3. **Fallback:** an existing owner-only VPN or isolated private LAN with a firewall allowing only the owner phone, plus a dedicated reverse proxy serving a handset-trusted HTTPS certificate (e.g. trusted organizational CA, or an existing owned hostname with DNS-validated certificate and private routing). Reverse proxy only to `http://127.0.0.1:8789`, preserve the external `Host`, overwrite `X-Forwarded-Proto` with `https` on **TLS connections only**, preserve browser `Origin`, and never proxy admin/worker sockets, the SIP webhook port, or the Pots Gateway from this origin. Deny plain HTTP, redirects on POST, and public ingress; do not expose port `8789` directly. Set proxy connection/rate/body/time bounds (64 KiB max request body, at least 15 seconds response time while the bounded provider setup/close completes), turn off body/header/request debugging and access logs that record sensitive input, and don't cohost other apps. Do not spoof scheme headers to serve over plaintext. Auth remains mandatory even with a VPN.
4. After authorization only: start `node src/cli.mjs serve --enable-paid-webrtc` with the configured origin and private sockets. Optionally add `--enable-paid-sip` in the **same** process if already approved; the two separate loopback ports are mutually exclusive at the session slot. Start the separately approved `node src/cli.mjs worker --enable-pots-effects` to exercise real dispatch. For a voice-only network test leave the worker off, and avoid preset commands unless you intend to leave a queued job.
5. From the private service-owner terminal, `node src/cli.mjs invite-web` prints a one-time URL which expires in two minutes. Transfer it to the owner phone in person or over a trusted private channel. Do not paste it into a public chat, browser sync/shared clipboard, access log, support ticket, or screen recording. Loading it redeems it into a scoped cookie; the app removes the token fragment from the address bar. Loading the URL does **not** start or charge a Live call. The owner has another two minutes after redemption to tap Start. Issuing another web invitation invalidates all unused web grants. If you are using SIP, let its current arm expire or close the current call first.

## First parked test on Safari / Chrome

- Connect the headset/car audio in the phone's OS **while parked**; test with the phone speaker first if the Bluetooth mic/output routing is uncertain. On a fresh link verify the displayed estimated cost; tap **비용에 동의하고 시작** once and allow microphone access. If permission is denied, grant it in site/system settings and retry while the invitation cookie is still valid. If autoplay is blocked, tap **소리 켜기** while parked. Confirm the system mic indicator and that opening the link alone does not activate it. Do not use in-app browsers. On each target OS, test the actual microphone permission modal: check that permission works when the page stays visible, and that switching away mid-prompt or while connecting prevents the call, stops any late microphone stream, and does not restart when you return. If the OS marks the page hidden during its permission modal, the app cancels; return to the page and tap Start again while the invitation is still valid.
- Confirm you can hear and reply immediately without touching the phone; speak naturally **while GPT-Live is speaking** and verify it hears you and yields, on speaker and headset. No push-to-talk, media recording, or file upload occurs. Output and microphone tracks operate independently and simultaneously; the handset/browser/Live model determine echo cancellation, routing, and what interruption sounds like. Car head units may fall back to the phone mic or speaker; the app does not select or force Bluetooth routing.
- With the approved Pots worker running, say exactly “회의 체크리스트 접수, 요청 끝.” Wait for the spoken receipt, then keep conversing and try “주간 리뷰 체크리스트 접수, 요청 끝.” End early via **대화 끝내기** or wait for the automatic pilot timeout. Verify the microphone indicator turns off, the provider session finalizes, the same bot's work continues, and the results go only to the verified private inbox. Spoken End is not implemented; ordinary phrases never act as a hangup command. Do not change OS settings, enter permissions, or operate the browser while driving.
- The page is a **foreground** experience. A browser-reported foreground exit cancels even microphone/ICE preparation, stops playback and any captured or late microphone stream, and prevents an offer from being sent while hidden. Closing it or leaving it triggers cleanup where supported; a server-side heartbeat deadline backs up page events. Screen lock, background/OS suspension, incoming calls, network transitions and Bluetooth reconnect can interrupt or end audio. No hands-free startup, lock-screen continuity, wake lock, CarPlay/Android Auto integration, or automatic reconnect is promised. Retest with the screen unlocked and an approved link while parked; never rely on continuous audio while driving.
- Check provider usage separately; there is no billing ledger in the bridge. If the sideband cannot confirm close, or a create times out before returning an ID, the persisted reservation blocks both transports across restarts; queued jobs remain claimable. With the service stopped, reconcile via the provider's project usage/support (and retry sideband recovery by restarting if the session ID is known). Do not delete the DB/WAL or blindly re-arm. If the final event cannot be retrieved, have the service owner review state and explicitly arrange an offline repair only after independent confirmation the provider session ended; there is deliberately no public override. A project kill switch or approved provider controls are the fallback if live usage continues.

## Why server-mediated SDP, not short-lived provider tokens?

The official GPT-Live WebRTC flow is an authenticated backend `POST /v1/live/sessions` with JSON `session` and `transport: {type: "webrtc", sdp}`. The `201` response yields `session.id` and `transport.sdp`: the service retains the ID for its trusted sideband `/v1/live/sessions/{id}/attach` and returns only the answer. WebRTC audio then goes directly between browser and provider; the service brokers setup/control and does not record or relay media. `oai-events` is a receive-only lifecycle data channel in this configuration; those provider events may include a session ID, configuration snapshot, or other lifecycle metadata, but no API credential. Commands are denied by Live's `session.client.data_channel` capability settings. The provider still reflects audio on sideband; the bridge discards it and doesn't persist it. No `session.start` is sent on the already-running session. WebRTC close is `session.close`/`session.closed` on sideband, not the Live SIP-only REST hangup.

A short-lived provider token, where a product supports it, reduces bootstrap work on the app server but puts an API credential in the browser and still needs authenticated issuance, scope and replay limits. The ephemeral client-secret recipe in the shared WebRTC guide is for **Realtime**, not the documented GPT-Live path. Do not port `/v1/realtime/client_secrets` or `/v1/realtime/calls` here. The invitation and cookie are app-specific grants, not provider credentials. Creating a session requires a freshly authorized browser, exact same-origin request, and explicit UI consent.
